# SPEC-SEC-001 구현 계획

## A. 사전 확인 사항 (plan 단계에서 읽은 사실)

- `src-tauri/build.rs`: `rerun-if-changed` 목록 뒤에 `tauri_build::build()` 호출. 앱 매니페스트 없음.
- `src-tauri/capabilities/main.json`: `windows: ["main"]`, `remote` 없음. 현재 권한: `core:default`, `core:window:allow-destroy`, `dialog:allow-open|save|message`, `opener:default`, `opener:allow-open-path`(`**`), `opener:allow-reveal-item-in-dir`(`**`), `shell:allow-execute`, `shell:allow-spawn`.
- `src-tauri/src/lib.rs:78-105`: `generate_handler!` 26개(file_ops 10, directory_ops 3, watcher 2, image_ops 5, browser_ops 1, ai 4, file_open 1).
- tauri-build 2.5.6 `acl.rs::app_manifest_permissions`: `AppManifest::commands(&[...])`가 명령마다 `./permissions/autogenerated/<명령>.toml`을 **빌드 작업 디렉터리(src-tauri) 아래에 쓴다**(`autogenerate_command_permissions(Path::new("./permissions/autogenerated"), …)`). 권한 식별자는 `allow-<명령-kebab>` / `deny-<명령-kebab>` 형태이고 앱 명령 권한은 capability에서 접두사 없이 쓴다. 생성 매니페스트 JSON의 앱 키는 `__app-acl__`(`APP_ACL_KEY`)이다. 이 두 가지(생성 위치, 접두사 없음)는 소스 판독이며 M1에서 실제 빌드로 확인한다.
- `.gitignore`는 `src-tauri/gen/`만 무시한다. `permissions/`는 무시하지 않는다.
- 프런트엔드 호출: `@tauri-apps/api/core` `invoke` 26개 명령(리터럴, `[a-z0-9_]+`로 센 값 — `ipc.ts`·`imageHandler.ts`가 `read_image_as_base64`류도 호출), `@tauri-apps/api/event` `listen`(`ai://chunk|done|error`, `file-changed`, `open-file`), `@tauri-apps/api/window` `getCurrentWindow().destroy()`, `@tauri-apps/plugin-opener` `openPath`·`revealItemInDir`. `plugin-shell`·`plugin-dialog` JS import 없음.
- `frontend-gates.yml`은 Rust 스텝 금지 방침. 기존 Rust 테스트는 로컬 `cargo test`로만 실행된다.

## B. 접근 방식 (사용자 검토 대상 — 가장 바뀔 가능성이 큰 결정부터)

1. **명령 목록 단일 출처**: `src-tauri/app_commands.rs`에 `pub const APP_COMMANDS: &[&str] = &[…26개…];`를 둔다. `build.rs`는 `include!("app_commands.rs")`로 읽고, 테스트도 같은 파일을 `include!` 한다. (대안: `build.rs`에 목록을 직접 쓰고 테스트가 `build.rs` 텍스트를 파싱 — 취약해서 기각.)
2. **capability 연결**: `main.json`에 `allow-read-file` … 26개를 추가한다. (대안: `permissions/default.toml`에 default 권한 집합 `default = ["allow-…"]`을 만들고 capability에는 `"default"` 하나만 — 간결하지만 `permissions/` 디렉터리 직접 관리가 늘어난다. 이 계획은 26개를 capability에 직접 나열하는 쪽을 기본으로 하며, 이유는 "어떤 명령이 허용됐는지"가 한 파일에서 보이기 때문이다.)
3. **드리프트 방지 테스트(Rust)**: `src-tauri/tests/app_acl.rs`(통합 테스트)가 (i) `lib.rs` 소스에서 `generate_handler![ … ]` 안의 `모듈::함수` 식별자를 뽑아 `APP_COMMANDS`와 집합 비교, (ii) `capabilities/main.json`의 `allow-*` 권한 집합이 `APP_COMMANDS`의 kebab 변환과 같은지 비교, (iii) 어떤 capability 파일에도 `"remote"` 키가 없는지 검사.
4. **프런트 계약 테스트(Vitest)**: `src/test/appCommandAcl.contract.test.ts`가 `src/**`의 `invoke('…')` 리터럴을 모아 `app_commands.rs`의 목록에 모두 있는지 검사한다(목록을 정규식으로 파싱).
5. **권한 정리(선택, REQ-008)**: grep으로 사용 근거가 없는 `shell:*`·`dialog:*` 권한을 제거하고 전 기능 스모크로 확인한다. 하나라도 거부 증상이 나오면 되돌리고 progress.md에 사유를 적는다.
6. **생성 파일 처리 (결정)**: `src-tauri/permissions/autogenerated/`는 매 빌드 재생성되는 산출물이므로 `.gitignore`에 `src-tauri/permissions/autogenerated/`를 추가하고 커밋하지 않는다(목록 이중 관리 방지). M1에서 실제 생성 위치를 확인해 경로가 다르면 `.gitignore` 줄만 맞춘다. 사용자가 커밋을 원하면 plan.md §D-1에서 뒤집는다.
7. **빌드 오류 전파**: `build.rs`는 `try_build(...)`의 `Err`를 `panic!`/`unwrap`이 아니라 메시지를 출력하고 비정상 종료해 빌드를 실패시킨다(조용히 삼키면 매니페스트 없이 빌드되어 현재 노출 상태로 돌아간다).
8. **build.rs 머리 주석**: 기존 주석의 `tauri_build::build()` 문구를 `build 함수`로 바꿔 AC-001 판정이 주석에 오탐되지 않게 한다.

## C. 마일스톤 (순서)

- **M0 — 기준선 탐침 (코드 변경 전, Windows·macOS 실기기)**
  - 탐침 HTML(`probe.html`, 저장소에 커밋하지 않고 progress.md에 본문을 적는다)을 현재 `main` 빌드로 연다. 본문:
    ```html
    <body><pre id="o"></pre><script>
    const r={internals:typeof window.__TAURI_INTERNALS__,href:location.href};
    (async()=>{
      const t=window.__TAURI_INTERNALS__;
      if(t){
        for(const [k,c,a] of [['read_file','read_file',{path:'C:\\Windows\\win.ini'}],
                              ['ai_policy_status','ai_policy_status',{}],
                              ['dialog_message','plugin:dialog|message',{message:'probe'}]]){
          try{ r[k]={ok:await t.invoke(c,a)} }catch(e){ r[k]={err:String(e)} }
        }
      }
      document.getElementById('o').textContent=JSON.stringify(r,null,1);
    })();
    </script></body>
    ```
    macOS에서는 경로를 `/etc/hosts`로 바꾼다. `write_file`·`delete_file`은 탐침에 넣지 않는다(파괴적).
  - 이동 탐침(M-2b용): 탐침 세트에 프레임 이동 탐침이 더해졌다. `probe-nav-a.html`은 asset 경로 HTML로, 링크 클릭과 `<meta http-equiv="refresh">` 두 방식으로 `probe-nav-b.html`(CSP 없는 asset 경로 HTML)로 이동시키고, `probe-nav-b.html`은 위 본문과 같은 방식으로 `read_file`·`ai_policy_status`·`plugin:dialog|message` 호출 결과와 `internals` 값을 화면에 쓴다. 두 파일은 untracked 디렉터리 `.moai/state/verify/sec-001-probe/`에 오케스트레이터가 만들며 저장소에 커밋하지 않는다(이 문서는 설명만 한다). 기준선(M0)에서는 이동 후에도 호출이 ok인지 기록하고, 적용 후(M2)에는 acceptance.md M-2b로 판정한다.
  - 기록: OS·빌드 SHA·`internals` 값·각 호출의 ok/err. 기준선에서 `read_file`이 ok면 위험 확정, 모두 err이거나 `internals`가 `undefined`면 위험 평가를 낮추고 코디네이터에게 보고(REQ-007).
- **M1 — 매니페스트·capability·테스트 (TDD)**
  1. RED: `app_acl.rs` 테스트와 Vitest 계약 테스트를 먼저 쓰고 실패를 확인한다(`APP_COMMANDS` 없음).
  2. GREEN: `app_commands.rs`, `build.rs`(`try_build`), `main.json` 26개 권한.
  3. 생성물 위치 확인 후 `.gitignore` 결정(위 B-6).
  4. `cargo build`·`cargo test --manifest-path src-tauri/Cargo.toml`, `npm test`, `npm run lint`, `npx tsc --noEmit`. 첫 `cargo build` 출력을 progress.md에 붙여 권한 식별자 중복 오류가 없음을 보인다(`permissions/autogenerated/*` 글롭이 자동 생성분을 두 번 읽는 경로가 있는지 확인, 있으면 `permissions_path_pattern`을 조정).
  4b. AC-004의 `node` 판정 명령을 실행해 `src-tauri/gen/schemas/*.json` 구조가 가정과 같은지 확인하고, 다르면 같은 의미로 보정해 기록한다.
  5. @MX: `app_commands.rs`에 `@MX:ANCHOR`(fan_in: build.rs + 테스트 + 보안 경계) 후보와 `@MX:NOTE`(새 명령 추가 절차).
- **M2 — 실기기 검증 (코드 변경 후)**
  - 같은 탐침을 다시 실행(Windows·macOS): `read_file`·`ai_policy_status`가 거부(err)되고 `main` 창 기능은 정상인지.
  - `tauri dev`(devUrl 출처)와 릴리스 빌드 양쪽에서 전 기능 스모크: 파일 열기·저장·다른 이름으로 저장·새 파일·이름 변경·삭제·폴더 열기·파일 감시·이미지 붙여넣기/삽입·내보내기·인쇄·AI 요청/취소·외부 열기(.md 더블클릭)·창 닫기 가드·`openPath`·`revealItemInDir`. 이 체크리스트는 acceptance.md M-3에 둔다.
  - 거부 발생 시 개발 빌드는 콘솔에 거부된 명령과 이유를 보여주므로(`webview/mod.rs:1807` debug 분기) 원인 권한을 바로 찾는다.
- **M3 — (선택) 플러그인 권한 정리와 문서**
  - REQ-008 후보 제거 시도. 결과를 progress.md에 기록. README/BUILD.md에는 변경이 필요 없다(내부 보안 변경). 새 명령 추가 절차는 `app_commands.rs` 머리 주석에만 둔다.

## D. 열린 결정 (사용자 소유 가능 — run 시작 전 코디네이터 확인 권장)

1. `autogenerated/` 커밋 여부: 기본은 `.gitignore`(§B-6 결정). 커밋을 원하면 알려야 한다.
2. REQ-008(미사용 `shell:*`·`dialog:*` 제거)을 이번 SPEC에서 실제로 할지: 기본은 M-3 스모크 통과 뒤 제거하고 거부가 나오면 그 권한만 되돌린다. 제거를 원치 않으면 REQ-008과 AC-007을 범위에서 뺀다.
3. `opener:allow-open-path`(`**`) 범위 축소는 범위 밖(기능 변경). 이후 별도 SPEC 필요 여부.
4. Windows 실기기 확보: M-1·M-2의 Windows 판정에 필요하다. 없으면 SPEC은 `implemented`까지만 닫는다(spec.md R-7).

## E. 위험 관리 요약

- 빌드는 통과하지만 런타임에서만 거부되는 유형이라 M2 스모크가 필수다. 프런트 계약 테스트·목록 일치 테스트는 "존재하는 명령"의 누락만 잡고, 동적 이름 호출(`invoke(variable)`)은 잡지 못한다 — M2 스모크가 보완한다(잔여 위험).
- Rust 테스트는 CI에 없다. 이 SPEC은 로컬 실행 결과를 증거로 남긴다.
