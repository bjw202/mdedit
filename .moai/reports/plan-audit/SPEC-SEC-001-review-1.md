## What I verified as TRUE (so the author need not redo it)
- `generate_handler!` has exactly 26 entries (lib.rs:79-104; breakdown 10/3/2/5/1/4/1 matches plan.md:L7).
- tauri 2.10.3 `webview/mod.rs:1801-1805`: ACL is checked only if `plugin_command.is_some() || has_app_acl_manifest`; `FETCH_CHANNEL_DATA_COMMAND` is exempt (so Channel traffic is not newly denied; the app uses no `Channel`).
- `asset` is NOT in the manager's `uri_scheme_protocols` map; it is registered only on the pending webview (`manager/webview.rs:307-318`, map insert at :98-109), so `is_local_url` (`webview/mod.rs:1680-1720`) classifies asset:// and http://asset.localhost as Remote. The SPEC's premise for REQ-004 (asset = remote) is correct.
- tauri-build 2.5.6 `acl.rs:274-290`: `AppManifest::commands` writes `./permissions/autogenerated/<cmd>.toml` relative to the build cwd (src-tauri), via tauri-utils 2.8.3 `autogenerate_command_permissions` which emits `allow-<kebab>` / `deny-<kebab>` (build.rs:289-303 of tauri-utils). Capability references use no prefix: `acl.rs:356` `get_prefix().unwrap_or(APP_ACL_KEY)`.
- `has_app_manifest` (acl.rs:408-413) becomes true with commands only, because the generated permissions make `manifest.permissions` non-empty. So `app_manifest(AppManifest::new().commands(..))` alone is enough; no `default.toml` needed.
- `build()` is just `try_build(Attributes::default())` + exit(1) on error (tauri-build lib.rs:440-453), so switching to `try_build` loses nothing as long as the error is propagated (D10).
- Events: `listen` goes through `plugin:event|listen` (plugin ACL, already enforced before this change and covered by `core:default`); Rust `emit` does not go through invoke. The app-manifest change cannot newly deny events. Only `getCurrentWindow().destroy()` additionally needs `core:window:allow-destroy`, which is already in main.json:L8.
- Frontend only imports `@tauri-apps/api/{core,event,window}` and `@tauri-apps/plugin-opener` outside tests; no `plugin-shell` / `plugin-dialog` import in non-test source; dialogs are Rust-side `DialogExt` (file_ops.rs:165,208; image_ops.rs:249; directory_ops.rs:83). REQ-008's removal candidates are sound.
- M0 probe is non-destructive (read_file, ai_policy_status, plugin:dialog|message only; write/delete excluded, plan.md:L42) and exercises the exact path of concern (the existing `sandbox="allow-scripts allow-same-origin"` asset iframe in HtmlFileViewer).
- Wry/WebView2 claims are labelled as unverified assumptions (spec.md:L30-L31, progress.md:L9). That labelling is correct and sufficient for those claims.

## Defects Found (structured defect-list)
D1. FRONTEND-COUNT-WRONG — spec.md:L32, L64 / plan.md:L10 / acceptance.md:L48 — Frontend string-literal `invoke` calls number **26**, not 24, and `read_image_as_base64` / `read_relative_image_as_base64` ARE called: `src/lib/tauri/ipc.ts:185,193`, consumed at `src/lib/image/imageHandler.ts:301,389`. The "24 + 2 unused/dynamic" claim is an artifact of a digit-blind regex: `invoke(<..>)?\(\s*['"][a-z_]+['"]` yields exactly 24 (reproduced) because `base64` contains digits; with `[a-z0-9_]+` it yields 26, and every one of the 26 `generate_handler!` commands is called. This is an unobserved claim presented as fact in a normative REQ, and AC-005 hard-codes the wrong number; a test written to the SPEC's regex would silently skip two commands. — Severity: major — Class: blocking — Required fix: change 24 -> 26 in spec.md L32/L64, plan.md L10, acceptance.md L48; delete the "미사용이거나 동적 호출" speculation; state that the contract test's name pattern is `[a-z0-9_]+` and assert the literal set equals the 26-entry set (or is a subset with an explicit expected count).
